Deployment phases
Target scenario (proposed) Future

Vision: PC traffic source with QinQ double-tagged VLANs feeding a daisy-chained BTS cluster — each BTS serving an 8-CPE PTMP sector with Raspberry Pi endpoints for automated throughput and telemetry. Full multi-BTS rollout is not feasible at this stage.

Initial deployment Current plan

Phase 1: One BTS at Proddatur serving eight CPE endpoints across the mapped coverage area. Raspberry Pi at each CPE runs throughput scripts and captures GPS/azimuth data for NMS validation.

Field test activities (planned)

Throughput

Multi-client iPerf / TRex runs per CPE — uplink & downlink at distance

GPS & azimuth

Lat/long, elevation, compass — birth certificate & NMS map accuracy

Link health

RSSI, SNR, MCS, retransmits — sustained monitoring over days/weeks

Alarms & events

Real-time fault injection — link loss, device reboot, NMS alarm path

QinQ / VLAN

Double-tagged traffic through BTS fronthaul — customer VLAN scenarios

Long-run soak

24 h+ stability — uptime, throughput drift, GPS relocation tolerance

ATPC / DCS

Adaptive power & channel selection under varying RF conditions

Sign-off evidence

Kiwi TCMS results, logs, PCAP, NMS exports for customer review

Typical field test flows (planned)

1 · Install & onboard

  1. Mount BTS at Proddatur hub; install CPEs at mapped locations
  2. Discover and onboard all devices in NMS
  3. Capture birth certificate (GPS, azimuth, RSSI, SNR)
  4. Verify topology and inventory in NMS GUI

2 · Throughput sweep

  1. Run iPerf from traffic PC via QinQ to each CPE/RPi
  2. Record UL/DL throughput per link at peak & off-peak
  3. Compare against lab baseline and SLA targets
  4. Export KPI data from NMS for reporting

3 · GPS & resilience

  1. Validate GPS coordinates vs physical install survey
  2. Induce link impairment; confirm alarm raise/clear in NMS
  3. Soak test over 24 h with power-backup failover check
  4. Package evidence for customer sign-off
